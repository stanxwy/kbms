## 1. 编码规范

### 1.1 代码风格统一标准

#### 1.1.1 Python（admin 后端）

| 规则 | 约定 | 级别 |
| --- | --- | --- |
| 缩进 | 4 个空格，禁止 Tab；续行对齐 8 空格（悬挂缩进相对起始位置） | 【强制】 |
| 行宽 | 120 字符（超出需换行），URL/长字符串除外 | 【强制】 |
| 空格 | 运算符（`=` `==` `+` `-` 等）两侧、逗号/冒号后各留 1 空格；函数形参默认值 `=` 两侧不加空格；括号内不加空格 | 【强制】 |
| 括号 | 函数/方法调用、下标、切片括号内不空格；条件表达式外层不加多余括号 | 【强制】 |
| 空行 | 顶层函数/类之间 2 空行；类内方法之间 1 空行；逻辑段落之间 1 空行 | 【强制】 |
| 引号 | 字符串统一双引号 `"`；docstring 用三双引号 `"""` | 【强制】 |
| 导入 | 标准库 → 第三方 → 本地，三段分组；绝对导入；禁止 `import *` | 【强制】 |
| 类型标注 | 所有公共函数/方法签名须标注参数与返回值类型；业务模型字段标注类型 | 【强制】 |
| 空文件/无用代码 | 禁止提交注释掉的死代码、未使用的导入/变量 | 【强制】 |

**工具链（强制通过 CI）**：`ruff format`（代码格式化）与 `ruff check`（代码检查），配置统一写入 `admin/pyproject.toml`，禁止本地任意覆盖。

示例：

```python
"""用户认证服务：签发/校验 JWT、密码散列。"""

from datetime import datetime, timedelta
from typing import Any

from jose import jwt

from app.core.config import settings


def create_access_token(subject: str, expires_delta: timedelta | None = None) -> str:
    """签发访问令牌。

    Args:
        subject: 用户唯一标识（user_id 字符串）。
        expires_delta: 过期时长，缺省取配置默认值。

    Returns:
        编码后的 JWT 字符串。
    """
    expire = datetime.utcnow() + (expires_delta or timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES))
    payload: dict[str, Any] = {"sub": subject, "exp": expire}
    return jwt.encode(payload, settings.SECRET_KEY, algorithm=settings.ALGORITHM)
```

#### 1.1.2 TypeScript / React（admin 前端）

| 规则 | 约定 | 级别 |
| --- | --- | --- |
| 缩进 | 2 个空格，禁止 Tab | 【强制】 |
| 行宽 | 120 字符 | 【强制】 |
| 引号 | 单引号 `'`；JSX 属性用双引号 `"` | 【强制】 |
| 分号 | 每条语句末尾加分号 | 【强制】 |
| 尾逗号 | 对象/数组/函数参数多行时保留尾逗号 | 【强制】 |
| 括号与空格 | 与 Prettier 默认对齐；对象字面量左右大括号内加 1 空格（`{ a: 1 }`） | 【强制】 |
| 导入顺序 | 类型 → 第三方库 → 本地模块 → 样式；成员按字母序 | 【强制】 |
| 组件定义 | 函数组件 + Hooks，禁止 class 组件；一个文件默认仅导出一个组件 | 【强制】 |
| 类型 | 禁止隐式 `any`；公共类型用 `interface`/`type` 显式声明 | 【强制】 |

**工具链（强制通过 CI）**：`Prettier`（格式化）+ `ESLint`（含 `@typescript-eslint` 与 `eslint-plugin-react-hooks` 规则），配置统一写入 `admin-frontend/.prettierrc`、`.eslintrc`。

示例：

```tsx
/**
 * 登录页：账号密码登录 + JWT 令牌持久化。
 */
import { Button, Form, Input } from 'antd';
import { useNavigate } from 'react-router-dom';

import { useUserStore } from '@/store/user';

interface LoginFormValues {
  username: string;
  password: string;
}

export default function LoginPage() {
  const navigate = useNavigate();
  const login = useUserStore((s) => s.login);

  const onFinish = async (values: LoginFormValues) => {
    await login(values);
    navigate('/');
  };

  return (
    <Form onFinish={onFinish}>
      <Form.Item name="username" rules={[{ required: true }]}>
        <Input placeholder="用户名" />
      </Form.Item>
      <Button type="primary" htmlType="submit">
        登录
      </Button>
    </Form>
  );
}
```

### 1.2 命名规则

#### 1.2.1 通用原则

1. **语义化**：命名应准确表达"做什么/是什么"，禁止 `a`、`b`、`tmp`、`data`、`info` 等无意义词；布尔变量用 `is_/has_/can_` 前缀。
2. **禁止魔法数字与魔法字符串**：抽为具名常量或枚举。
3. **长度**：命名以 2–5 个词为宜，避免过长；缩写仅允许通用且团队公认者（`id`、`url`、`api`、`json`、`http`）。

#### 1.2.2 Python 命名

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 模块/文件 | `snake_case` | `permission_engine.py` |
| 包/目录 | `snake_case` 短名 | `app/api/v1` |
| 函数 | `snake_case`，动词开头 | `check_permission`、`create_unit` |
| 变量 | `snake_case` | `unit_ids`、`page_size` |
| 类 | `PascalCase` | `PermissionEngine`、`KnowledgeUnit` |
| 常量 | `UPPER_SNAKE_CASE` | `FAQ_MATCH_THRESHOLD` |
| 私有成员 | 单下划线前缀 | `_validate_token` |
| 数据库表 | `snake_case` 复数 | `knowledge_units` |
| 数据库字段/API 字段 | `snake_case`，与 Pydantic 对齐 | `unit_code`、`source_file_name` |

#### 1.2.3 TypeScript 命名

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 变量/函数 | `camelCase` | `fetchUnits`、`tableLoading` |
| 组件 | `PascalCase` | `KnowledgeList`、`LoginPage` |
| 类型/接口 | `PascalCase`（不加 `I` 前缀） | `KnowledgeUnit`、`PageResult<T>` |
| 常量/枚举 | `UPPER_SNAKE_CASE` | `FAQ_MATCH_THRESHOLD` |
| 枚举成员 | `PascalCase`（enum）或 `UPPER_SNAKE_CASE`（const object），二选一保持一致 | `Role.ADMIN` |
| Hook | `use` 前缀 camelCase | `usePermission`、`useUnits` |
| 文件名 | 组件 `PascalCase.tsx`，工具 `camelCase.ts` | `KnowledgeList.tsx`、`request.ts` |

### 1.3 注释规范

**原则**：注释解释"为什么"而非"是什么"；命名已能表达意图处不写冗余注释；优先用类型/命名提升可读性。

| 类型 | 位置 | 格式与内容要求 | 级别 |
| --- | --- | --- | --- |
| 文件头说明 | 每个模块首行 | 单行 `"""模块职责与关键约束。"""`（Python）或 `/** 模块职责 */`（TS） | 【强制】 |
| 函数/方法说明 | 每个公共函数/方法上方 | docstring 含：一句话职责、参数（`Args`）、返回（`Returns`）、可能抛出的异常（`Raises`）、副作用（可选） | 【强制】 |
| 复杂逻辑说明 | 关键分支/算法上方 | 说明为什么这样写、隐含约束、算法要点；每段 2–3 行内 | 【强制】 |
| 关键业务规则 | NOT NULL/唯一值/状态机变更处 | 注明业务含义与越界后果 | 【建议】 |
| TODO/FIXME | 临时占位 | 必须附注责任人与 issue/版本号，评审时逐条清理 | 【强制】 |

Python docstring 统一风格为 **Google 风格**；TypeScript 统一 JSDoc。禁止使用行尾无意义注释（如 `// 赋值`）。

## 2. 测试规范

### 2.1 测试分层与工具

| 层级 | 覆盖对象 | 工具 | 运行时机 |
| --- | --- | --- | --- |
| 单元测试（Unit） | 后端服务/引擎函数、前端纯函数与 Hook | pytest + pytest-asyncio；vitest | 每次提交 |
| 集成测试（Integration） | DB 读写、鉴权中间件、RAG 客户端契约 | pytest + 测试库（PostgreSQL 隔离 schema 或 testcontainers）；vitest + MSW | 每次合并 |
| 端到端（E2E） | 导入→配权→问答→看板→沉淀主链路 | 手工验收 + compose 一键链路脚本 | 阶段里程碑/发布前 |

> 约定：测试文件命名 `test_*.py` / `*.test.ts`，与源码同目录独立 `tests/` 镜像结构；每个被改动特性必须有对应测试用例。

### 2.2 测试场景与验收标准

#### 2.2.1 功能测试（正常流程 + 边界条件）

| 场景 | 覆盖点 | 验收标准 |
| --- | --- | --- |
| 正常流程 | 登录签发、知识单元 CRUD、部门树、四维权限放行、FAQ 审核发布、问答 SSE 全字段 | 输入合法时返回码 200、数据结构与 SPEC §4 契约完全一致、状态机按预期迁移 |
| 边界条件 | 空列表、分页末页、`page_size` 为 0/1/最大值、名称长度上限、时间区间首尾、幂等重复导入（同 `source_file_name`） | 不抛 500；空结果返回空集合与正确 `total`；越界分页参数按默认值或 422 处理；重复导入不产生脏数据 |
| 权限边界 | 停用用户、无权限用户、子部门成员命中祖先部门、混合多实体任一命中 | 判定结果与权限矩阵逐项一致，无越权放行 |

#### 2.2.2 异常处理测试（非法输入 + 错误状态）

| 场景 | 覆盖点 | 验收标准 |
| --- | --- | --- |
| 非法输入 | 非法类型/格式（非数字 id、错误邮箱/枚举值、超长字符串）、缺失必填字段、SQL 注入片段、XSS 脚本 | 统一返回 422（参数校验）或 400，错误消息不含堆栈/内部信息；注入片段被安全处理不生效 |
| 未认证/未授权 | 缺失/过期/伪造 Token、越权调用他人资源、无操作权限调接口 | 未认证返回 401；无权限返回 403；统一下游不执行副作用 |
| 资源/状态错误 | 访问不存在资源（404）、删除含子/成员的部门、修改审核中 FAQ、重复创建唯一约束冲突 | 返回对应 4xx + 明确 `code/message`，事务回滚，无半写状态 |
| 外部依赖异常 | RAG `RAG_BASE_URL` 不可用、超时、返回非 200 | 记录结构化错误日志，向用户返回友好 5xx；不将 RAG 异常栈直抛前端 |

#### 2.2.3 性能相关场景（负载 + 并发）

| 场景 | 覆盖点 | 验收标准 |
| --- | --- | --- |
| 并发 | 同一用户并发问答、并发写入 `qa_access_logs`、并发导入触发幂等 | 无数据竞争/重复写；`qa_access_logs` 异步写不阻塞主链路；总量守恒 |
| 负载基线 | 列表/看板聚合接口在基准数据量（1 万单元、100 万日志）下的响应 | P95 响应：列表 ≤ 500ms、看板聚合 ≤ 2s；索引命中（EXPLAIN 无全表扫描） |
| 常见接口延迟 | `check-permissions`、`recall 鉴权过滤` | 单次判定 ≤ 100ms；权限判定在召回后批次完成 |
| 流式稳定性 | SSE 长连接断线重连、客户端中断 | 服务端及时释放连接与任务，无泄漏；断线不写坏日志 |

#### 2.2.4 覆盖率与门禁（DoD）

| 指标 | 阈值 | 级别 |
| --- | --- | --- |
| 后端核心逻辑行覆盖率 | ≥ 80%（T3 数据权限引擎、T1 鉴权模块须 ≥ 90%） | 【强制】 |
| 前端组件/Hook 覆盖 | 关键业务组件（登录、知识维护、对话、权限选择）有单测 | 【强制】 |
| 回归通过率 | 合并前全部用例绿色，无 skip 关键用例 | 【强制】 |
| 报告产出 | CI 生成 coverage 报告并归档，下降 5% 以上即阻断合并 | 【强制】 |

## 3. 安全规范

### 3.1 输入验证规则

| 类别 | 规则 | 级别 |
| --- | --- | --- |
| 类型 | 所有外部输入经 Pydantic（后端）/ 表单校验（前端）强校验，字段严格类型化，禁止用 `str` 承载需要枚举/数值的输入 | 【强制】 |
| 格式 | 邮箱、电话、日期、`unit_code` 等用正则/validator 校验；枚举字段用 `Literal`/`Enum` 限定取值 | 【强制】 |
| 长度 | 所有字符串字段设 `max_length`（如名称 ≤ 128、用户名 ≤ 32、密码 8–64、描述 ≤ 512、问题/回答 ≤ 2048） | 【强制】 |
| 范围 | 数值字段设 `gt/ge/le` 边界；`page` ≥ 1、`page_size` 有上限（如 ≤ 100） | 【强制】 |
| 白名单 | 排序字段、筛选字段、导出格式等参数须白名单枚举校验，禁止拼接进原始 SQL/命令 | 【强制】 |
| 拒绝规则 | 未声明字段（`extra="forbid"`）、空字符串必需项、控制字符（`\0`、换行注入）一律拒绝 | 【强制】 |
| 富文本/文件 | 上传文件校验 MIME + 大小上限 + 文件名白名单字符；Markdown/富文本渲染做 XSS 净化（前端 `react-markdown` 不启用 raw HTML） | 【强制】 |

### 3.2 认证授权机制

#### 3.2.1 身份验证

| 项 | 规则 | 级别 |
| --- | --- | --- |
| 凭据 | 密码经 bcrypt（`passlib`）单向散列存储，禁止明文/可逆加密 | 【强制】 |
| 令牌 | JWT 无状态签发，含 `sub`/`exp`/`iat`；访问令牌短期（建议 ≤ 30 分钟），刷新令牌分离存储并支持撤销 | 【强制】 |
| 校验 | 每个受保护接口经统一鉴权中间件：验签 → 验过期 → 查用户状态（停用即拒绝） | 【强制】 |
| 失败处理 | 登录失败/令牌无效返回统一 401，不泄露「用户名是否存在」差异信息 | 【强制】 |
| 会话 | 登出后令牌作废；刷新令牌轮换，旧令牌失效 | 【建议】 |

#### 3.2.2 权限分级控制

| 项 | 规则 | 级别 |
| --- | --- | --- |
| 操作权限（RBAC） | 接口级鉴权基于 `role_permissions` 的 `permission_type`（`menu`/`button`），支持用户-角色多对多；前端按钮按权限码渲染，后端接口必须二次校验（不信任前端） | 【强制】 |
| 数据权限（四维） | 知识单元访问经数据权限引擎：`global/department(含祖先)/role/user` 任一命中放行；停用用户直接拒绝 | 【强制】 |
| 最小权限 | 默认拒绝（default deny）；新功能默认不给任何角色授权 | 【强制】 |
| 越权防护 | 所有"按 id 操作资源"接口校验资源归属/权限，禁止仅凭 id 直接放行 | 【强制】 |
| 管理员 | `system_admin` 等高权限角色的关键操作（删除、发布）记录操作审计日志 | 【强制】 |

### 3.3 数据保护措施

| 类别 | 规则 | 级别 |
| --- | --- | --- |
| 敏感数据加密 | 密码 bcrypt 散列；JWT 密钥、DB 密码从环境变量/密钥管理注入，禁止硬编码入代码或提交仓库 | 【强制】 |
| 传输安全 | 生产环境全量 HTTPS（TLS ≥ 1.2）；前后端、admin↔RAG 之间敏感调用走 HTTPS 或内网 | 【强制】 |
| 存储安全 | 数据库连接使用最小权限账号；`SECRET_KEY` 等敏感配置启用加密存储；日志/看板脱敏（隐藏密码、Token、完整身份证/手机号） | 【强制】 |
| 注入防护 | SQL 一律走 SQLAlchemy ORM/SQL 参数绑定，禁止字符串拼接 SQL；命令执行禁用 | 【强制】 |
| 跨站防护 | 配置 CORS 白名单（仅允许前端合法 Origin）；Cookie 设 `HttpOnly`/`Secure`/`SameSite`；CSRF 敏感写接口校验 | 【强制】 |
| 限流与防刷 | 登录/问答/导出等高频接口配置速率限制（如登录 5 次/分钟/IP），防暴力破解与资源滥用 | 【建议】 |
| 依赖安全 | 定期 `pip-audit` / `npm audit`，高危漏洞依赖阻断发布 | 【强制】 |
| 审计日志 | 登录、权限变更、知识删除、FAQ 发布等关键操作落审计日志（操作人/时间/对象/结果/IP） | 【强制】 |

## 4. 规范执行与检查点

| 检查点 | 编码规范 | 测试规范 | 安全规范 |
| --- | --- | --- | --- |
| 开发 | IDE 统一 `.editorconfig`；提交前 `pre-commit` 跑 ruff/prettier | 特性开发同步补测试 | 输入校验、参数化查询、脱敏日志 |
| 代码评审 | 风格/命名/注释逐项核对 | 用例覆盖与验收标准 | 越权、注入、敏感数据 |
| CI | `ruff check` + `prettier --check` 不通过即阻断 | coverage 门禁 + 回归全绿 | `pip-audit`/`npm audit` 高危阻断 |
| 里程碑验收 | — | M1–M5 对应 DoD 用例通过 | 权限矩阵/数据脱敏抽查通过 |

> 三者优先级：**安全规范 > 测试规范 > 编码规范**。当风格与安全相冲突时，以安全规范为准。
